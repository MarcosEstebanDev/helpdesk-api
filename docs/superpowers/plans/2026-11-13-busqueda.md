# Búsqueda — Plan de implementación

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Filtro `?q=` en `GET /tickets` que busca en asunto, descripción, comentarios (notas internas solo para el equipo) y número, con FTS de Postgres en español.

**Architecture:** Columnas `search_vector` generadas + GIN; una función pura del dominio traduce el texto a `tsquery`; el read model obtiene en SQL los ids que coinciden (máx. 1000, los más recientes) y los combina con el `findMany` existente.

**Spec:** `docs/superpowers/specs/2026-11-13-busqueda-design.md`

## Global Constraints

- Palabras = secuencias de letras/números Unicode; máx. 8; cada una `palabra:*`, unidas con ` & `.
- `#n` o `n` (solo dígitos) → además busca `number = n`.
- Comentarios visibles según `visibleTo(rol)`; un VIEWER nunca encuentra un ticket solo por una nota interna.
- Tope de coincidencias: `SEARCH_MATCH_LIMIT = 1000`, las más recientes.
- `q` máx. 200 caracteres (400 si más). `q` vacío o sin palabras válidas = sin filtro.
- `migrate diff` vacío; commits con `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

1. Un VIEWER busca una palabra que solo está en una nota interna → no aparece el ticket. (e2e T3)
2. Texto con sintaxis de tsquery (`a & | ! (b`, `:*`, comillas) → 200, nunca 500. (unit T1 + e2e T3)
3. "facturacion" encuentra "facturación"; "fact" encuentra "facturas". (e2e T3)
4. `q` + otro filtro (estado, etiqueta) + paginación por cursor → respeta los dos. (e2e T3)
5. Otra organización con la misma palabra → no se mezcla. (e2e T3)
